Install · v0.0.5

macOS on Apple Silicon. Unsigned. Apache-2.0.

Two ways in: download the release and verify it, or build from source. Both are explained below, including the part where macOS refuses to open the download and what the command that fixes it actually does.

Use v0.0.5 or later. No earlier build could answer a question on a machine that was not the one that built it. v0.0.0 left the MLX worker script out of the bundle and declared no macOS folder-usage strings, so it could neither load a model nor read a folder you had granted — fixed in v0.0.1. But the interpreter that worker runs on was never in any bundle either, and the instructions this page used to give you started one step after the step that was missing. v0.0.5 installs it for you. If you have an earlier build, replace it.

What you need

RequirementDetail
Mac with Apple Silicon An M-series chip. Reference hardware for the project is an Apple Silicon Mac with 16 GB. There are no degradation tiers — if it does not run there, that is a bug rather than a configuration.
Disk for the index Everything lives under ~/.local/share/marrow/, per-user, never machine-wide. MARROW_DATA_DIR overrides it.
Nothing, to search Keyword and filename search need no model, no GPU and no network. That is a hard rule of the project.
Nothing, to answer locally Local generation and embedding run in an MLX worker process, and the Models page installs it: one button, a 193 MB download that brings its own Python, unpacked to about 626 MB under ~/.local/share/marrow/runtime/. Nothing else on the machine is touched and no Python of your own is needed. Or skip it and point Marrow at a cloud endpoint instead.

Download and verify

Four files are attached to the latest release. Take the app, the CLI, or both.

The names below carry the version, so there is no stable link to any one of them — take them from the release page. This page used to link straight at latest/download/Marrow_0.0.3_aarch64.dmg, which stopped resolving the moment a release after v0.0.3 existed: latest follows the newest release, and the filename did not.

FileWhat it isSize
Marrow_<version>_aarch64.dmg The desktop app, as a disk image. This is where Ask lives. 9.8 MB
Marrow-v<version>-aarch64.app.zip The same app, zipped, if you would rather not mount a disk image. 9.8 MB
marrow-cli-v<version>-aarch64-apple-darwin.tar.gz The marrow binary on its own — indexing, search, and the MCP server. No GPU, no model, no network. 5.9 MB
SHA256SUMS.txt SHA-256 for each of the three, generated by the release workflow at bundle time. 299 B

  1. Verify what you downloaded

    Put SHA256SUMS.txt in the same directory as the files you took and check them. --ignore-missing is there so it does not complain about the two files you did not download. 

    cd ~/Downloads
shasum -a 256 --ignore-missing -c SHA256SUMS.txt

    Every line must end in OK. If any line says FAILED, stop — delete the file and download it again.

  2. Install the app

    Open the disk image and drag Marrow.app to /Applications, or unzip it there.

  3. Install the CLI

    The tarball holds a single binary called marrow. Put it anywhere on your PATH. 

    tar -xzf marrow-cli-v0.0.5-aarch64-apple-darwin.tar.gz
sudo mv marrow /usr/local/bin/
marrow --version

macOS will refuse to open it. Here is why, and the fix.

This build is not signed and not notarised. Signing requires a paid Apple Developer account, and this is a personal project with one author. So Gatekeeper does exactly what it should with an unsigned binary downloaded from the internet: it refuses to run it, and the dialog does not offer you a way through.

Anything downloaded by a browser gets an extended attribute called com.apple.quarantine attached to it. That attribute is what Gatekeeper checks. The command below removes it — -d deletes one attribute, -r walks into the bundle so every file inside it is cleared too — from that one path and nothing else.

On macOS Sequoia and later, right-clicking and choosing Open no longer works as a way through. If you would rather not run a command, the equivalent is System Settings → Privacy & Security: after the first refusal there is an Open Anyway button near the bottom.

If the app bounces once in the Dock and vanishes with no dialog at all, you have v0.0.1 or v0.0.2. Those two shipped with an invalid code signature. macOS does not prompt in that case — on Apple Silicon a bad signature is fatal, and the app is killed before it can draw anything, which is why nothing tells you what happened. No command fixes those builds. Download v0.0.3 or later, which is signed correctly. 

# The app:
xattr -dr com.apple.quarantine /Applications/Marrow.app

# Or the CLI, if that is what you took:
xattr -dr com.apple.quarantine /usr/local/bin/marrow

Read that command before you run it, and be suspicious of anyone who tells you not to bother. It disables a real protection for one specific file. The only reason it is safe here is that you verified the checksum against the release above and can read the source that produced it.

Building from source is the honest alternative and avoids the question entirely — nothing you compiled yourself is ever quarantined. It takes a few minutes.

Build from source

Rust 1.85 or newer, Node 22 and pnpm 9. The desktop app additionally needs the Tauri CLI. 

git clone https://github.com/CasualOffice/marrow
cd marrow

# The CLI on its own — this is all you need for indexing,
# search and the MCP server.
cargo build --release -p marrow-cli
./target/release/marrow --version

# The desktop app. The front end is built first, because the
# Tauri build reads ui/dist at compile time.
cd crates/desktop/ui && pnpm install && pnpm build && cd ..
cargo install tauri-cli --version "^2" --locked
cargo tauri build

These are the same commands the release workflow runs, in the same order — see .github/workflows/release.yml. The bundle lands in target/release/bundle/.

Why there is no Linux or Windows build

Not "we have not got round to it". Most of the code is already portable — the platform-specific pieces are behind cfg gates and the workspace compiles for both targets. One function is what stops it.

Marrow has to decide, before opening a file, whether that file is really on this disk or is a cloud placeholder — an iCloud stub, a OneDrive file marked recall-on-open. Reading a placeholder downloads it, and pointing an indexer at a home directory full of them would quietly pull hundreds of gigabytes over someone's connection and onto their disk. Never doing that is a hard rule of the project.

Only the macOS implementation of that check exists. The stub for every other platform fails closed: it reports every file as unavailable, so nothing is read and nothing is hashed. A Linux or Windows build would therefore start up, refuse to index a single file, and be right to. Shipping it would be shipping a program that does nothing.

Three further things are Apple frameworks rather than portable code: PDF text with per-character boxes comes from PDFKit, text inside images comes from Vision, and local generation is MLX on Apple Silicon — there is no CPU inference path to be slow on. A port would need a placeholder check per platform, a keyring backend other than apple-native, a hardware probe, and CI on real runners, because SQLite and Tree-sitter build C and a Mac cannot honestly cross-check them.

No GPU, or not on a Mac at all? Every part of Marrow that answers questions can be pointed at any OpenAI-compatible endpoint instead — see adding a cloud model. Search itself never needs one.
