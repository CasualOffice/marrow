Guides / Use it from Claude Code or another agent

Guide 3

Serve your index to the agent you already use

marrow mcp speaks MCP over stdio and exposes fourteen tools. It is an adapter: it computes nothing the CLI cannot also reach, so anything it tells an agent you can reproduce in a terminal.

  1. Index something first

    The server serves an index; it does not build one. If you have not done it yet, grant a folder and index it — one command each.

  2. Register the server

    With Claude Code:

    claude mcp add marrow -- marrow mcp

    With any client that takes an mcpServers block — Codex, Cursor, and most others — this is the whole configuration: 

    {
  "mcpServers": {
    "marrow": {
      "command": "marrow",
      "args": ["mcp"]
    }
  }
}

    Use an absolute path to the binary if it is not on the PATH your client inherits. The repository's own .mcp.json points at ./target/release/marrow for exactly that reason.

    Protocol traffic uses stdout, so nothing else may write there. Marrow's own narration goes to stderr; if you wrap the command in a shell script, make sure your script does too.

  3. Know which tool to reach for

    Seven tools answer questions about files that already exist. Four either write a file or send a request off this machine, and they are kept in a separate list in the source for that reason — the boundary should be visible from tools/list without reading the descriptions.

    Read

    ToolWhat it is for
    search Ranked excerpts with a path, a citable line span and a structural breadcrumb. Matches on words, not substrings. Hand it the question, not keywords — any word may match by default, and match: "all" or "phrase" tighten it. The mode that ran is echoed back.
    search_literal Scans the files themselves for an exact string or regex, ignoring the index. This is what finds }); or TODO(name). Slower, and it only sees files on this disk.
    read_file An indexed file, or one line range of it. Prefer a range: excerpts keep the answer citable and the context small.
    read_table Tables as structure — rows, columns, typed values, and the cell range every value came from. Use it instead of read_file on any spreadsheet or Markdown/HTML table.
    file_info Everything known about one file: stable identity, content hash, previous paths if it moved, version count, tier state, index status. The disk is checked, not just the index.
    list_workspaces The granted folders with their counts and freshness. Try this first when a search returns nothing — the answer is often that the folder was never granted.
    index_status Index health, and specifically the gap between "files indexed" and the much smaller "files searchable". A search that misses something is often explained here.

    Write, and reach outward

    ToolWhat it is for
    create_file Writes a text file into a granted workspace, at a workspace-relative path.
    create_diagram Writes a Mermaid diagram. .md wraps it in a fenced block; .mmd writes the source bare. Refuses source that does not start with a diagram type, because prose in a diagram file renders as nothing at all.
    create_page Writes a self-contained HTML page. The title is escaped; the body is not, so it may carry markup.
    fetch_url Fetches one HTTPS page and returns its readable text. This sends a request off the machine.

  4. Read three fields in every result

    • provenance — exact, degraded or approximate. A value recovered from a degraded grid should not be quoted with the confidence of one read out of a clean spreadsheet.
    • origin — a result marked self_written was produced by an agent through these tools and must not be cited as independent evidence.
    • coverage, on search_literal — complete: false means the scan did not look everywhere, so "no match found" is not the same as "not present". Every skipped file is counted with its reason.

    Two more worth knowing. read_table's header_row may be null — a header is inferred, never assumed to be the first row, and an ambiguous top row is reported as having none rather than being given one; check header_confidence before relying on column names. And reconstruction says how well the grid came back: exact, degraded or failed.

What the server refuses

These are not overridable, and the refusal always names the reason:

  • Cloud-only placeholder files are never opened. Not by read_file, not by read_table, and search_literal skips them without opening them — because opening one downloads it.
  • A workspace name that does not exist is an error, not an empty result. Empty is indistinguishable from a genuine miss.
  • Writes stay inside the workspace. A path that resolves outside it, a protected or excluded subtree, or a name the filesystem would mangle are all refused. Paths are canonicalised and re-checked at write time, not only at validation time.
  • There is no unconditional overwrite. Every write tool takes expect: "new" creates and refuses if anything is there, or {"replacing": "<blake3 hex>"} with the digest you got when you last read the file. The staleness check runs immediately before the write, because you may have the file open in your editor.
  • Everything written is marked as written by this system and excluded from evidence. Search will find it; a later answer cannot cite it as corroboration. Edit it yourself and it becomes yours again.
  • fetch_url is fenced hard. Plain http is refused, any port but 443 is refused, and any host that resolves to loopback, a private range, link-local or carrier-grade NAT is refused — checked on the resolved address and re-checked on every redirect, because a hostname that resolves to 127.0.0.1 is the whole attack. Only hosts you have already allowed can be fetched: this surface has no way to ask, so consent is pre-registered in net-allow.txt in Marrow's data directory. A host that is not listed is refused, and the refusal names the file and the line to add.

The MCP search tool is keyword-only. It goes through the same fusion and the same post-fusion multipliers as every other surface, but it passes no vector index: the meaning-based branch needs an embedder, and a stdio server has to start instantly. marrow search --semantic and the desktop app both have it. The result reports which branches actually ran, so a caller is never left to assume.
